# Financial Accounts — Requirements Document

**Service:** Invistus Banking Service
**Module:** Personal Finance — Financial Accounts
**Document date:** 2026-04-10

---

## 1. Overview

Financial Accounts are the central entity of the personal finance module. A user can:

- **Create** accounts and cards manually, choosing from a predefined taxonomy of types and subtypes.
- **Edit** supported account metadata in the current UI (name, institution, subtype-specific bank/card fields).
- **List** all active accounts belonging to their tenant, used throughout the UI to scope transactions, bills, and monthly summaries.
- Associate an account with a **known issuer** (from a seeded institution catalogue) or enter a **custom institution name**.
- Record an **initial balance** at creation time, which auto-creates a `BALANCE_ADJUSTMENT` transaction.
- Persist future-use metadata already present in the domain/schema (`themeColor`, inclusion flags, `linkedBankAccountId`, foreign currency), even when the current `finance-transactions` UI intentionally keeps those inputs hidden.
- View transactions in the account scope. The current `finance-transactions` UI uses **calendar-based display** for all supported account types; bill-specific display remains deferred.

Soft-delete / deactivation is **not implemented yet** in the GraphQL API or in the current `finance-transactions` UI. It remains backlog work.

Open Finance (Pluggy) sync is **out of scope** for the current phase (Phase 5). Fields required for future integration (`connectionStatus`, `consentExpiresAt`, `lastSyncAt`, `providerItemId`) are present in the schema but are null for all manually managed accounts.

## 2. Account Types & Subtypes

### Top-level Types (`FinancialAccountType`)

Defined in `domain/account/FinancialAccountEnums.kt` and enforced by a DB `CHECK` constraint in `V0_3__create_banking_accounts.sql`.

| Type | Description |
|---|---|
| `BANK` | Bank accounts — checking, savings, salary, digital, joint |
| `CREDIT` | Credit and charge cards (post-pay billing cycle) |
| `PAYMENT` | Payment accounts, prepaid cards, and benefit vouchers |
| `CASH` | Physical cash wallet |
| `INVESTMENT` | Investment accounts (brokerage, fixed income, pension, crypto) |
| `LOAN` | Loan and financing tracking (liability, no cash flow generated by account itself) |
| `ASSET` | Physical asset tracking for net worth (property, vehicle, other) |
| `BENEFIT` | Government-managed benefit accounts (FGTS, INSS — Caixa Econômica Federal) |

The domain model supports all types above. However, the current `finance-transactions` account drawer only exposes two manual entry points: `BANK` ("Conta Bancária") and `CARD` ("Cartão"), which cover BANK accounts plus card-like CREDIT / PAYMENT subtypes used in transaction scope.

### Type-specific Nested Data

**`BankData`** — populated only when `type = BANK`:

| Field | Type | Notes |
|---|---|---|
| `branchCode` | String? | Agency number (agência) |
| `number` | String? | Account number |
| `checkDigit` | String? | Verification digit |
| `maskedNumber` | String? | Display-safe partial number |

**`CardData`** — populated when subtype is `CREDIT_CARD`, `CHARGE_CARD`, `PREPAID_CARD`, or `VOUCHER_CARD`:

| Field | Type | Notes |
|---|---|---|
| `maskedNumber` | String? | Card number, last 4 digits extracted for matching |
| `bin` | String? | First 6 or 8 digits |
| `cardNetwork` | `CreditCardNetwork`? | VISA, MASTERCARD, AMERICAN_EXPRESS, DINERS_CLUB, HIPERCARD, ELO, BANDEIRA_PROPRIA, OUTRAS |
| `cardLevel` | `CreditCardLevel`? | STANDARD, GOLD, PLATINUM, INFINITE, BLACK |
| `creditLimit` | BigDecimal? | Total credit limit |
| `availableCreditLimit` | BigDecimal? | Available credit (computed or entered) |
| `minimumPaymentPercentage` | BigDecimal? | Minimum payment percentage |
| `closingDay` | Int? | Optional billing-cycle metadata for cards when known; when present must be a valid day-of-month (`1..31`) |
| `dueDay` | Int? | Optional billing-cycle metadata for cards when known; when present must be a valid day-of-month (`1..31`) |
| `linkedBankAccountId` | UUID? | Optional link to a BANK account so `payBill` can create the debit leg on that bank account |

`closingDay` and `dueDay` are independent optional integers. The product does **not** require pairing or ordering between them. Cards with unknown or non-applicable billing-cycle data are still valid and continue to use calendar-based transaction display in the current UI.

## 3. Business Rules

### 3.1 Issuer Resolution

Source: `FinancialAccountService.create()` / `update()` — `service/account/FinancialAccountService.kt`

- Either `issuerId` (FK to `banking.issuers`) or a non-blank `issuerName` (free text) **must** be provided. Providing neither throws an `IllegalArgumentException`.
- The two options are mutually exclusive. When `issuerId` is provided, `issuerName`, `issuerCountry`, `issuerCompeCode`, and `issuerIspb` are populated from the issuer record, overriding any user-supplied values.
- When `issuerId` is null and `issuerName` is provided, this is treated as a "custom institution": `issuerName` is stored verbatim, all issuer code fields (`issuerCountry`, `issuerCompeCode`, `issuerIspb`) are set to null.

### 3.2 Account Name Resolution (on create)

Source: `FinancialAccountService.create()`

The effective name is resolved in this priority order:
1. `command.name` if non-blank
2. The name of the resolved `Issuer` entity (when `issuerId` is valid)
3. `command.issuerName` (custom institution name)
4. If none of the above resolves, an `IllegalArgumentException` is thrown.

On **update**, if `command.name` is blank, the existing account name is preserved.

### 3.3 Initial Balance

Source: `FinancialAccountService.create()`

- Only applicable at creation (not on update). The `UpdateFinancialAccountCommand` does not include `initialBalance`.
- When `initialBalance` is provided:
  - It **must be non-zero** (zero value throws `IllegalArgumentException`).
  - `initialBalanceDate` **must also be provided** (null throws `IllegalArgumentException`).
  - `initialBalanceDate` must not be older than `DateWindowPolicy.MAX_PAST_YEARS = 5` years from today. Violation throws `ValidationException` with error code `TRANSACTION_DATE_OUTSIDE_ALLOWED_WINDOW`.
- A `BALANCE_ADJUSTMENT` transaction is auto-created with:
  - `description = "Saldo inicial"`
  - `status = POSTED`
  - `creditDebitType = CREDIT` if balance > 0, `DEBIT` if balance < 0
  - `amount = initialBalance.abs()`
  - `currencyCode` matching the account's currency

The UI restricts the initial balance field to bank accounts only (`selectedType !== 'CARD'`) and to the create flow only (hidden when editing).

### 3.4 Account Type Lock on Update

Source: `FinancialAccountService.update()`

- If the existing account has `type = BANK`, the update command **must** also specify `type = BANK`. Changing away from BANK is rejected.
- If the existing account has any type other than `BANK`, the update command **must not** specify `type = BANK`. Changing to BANK is rejected.
- This prevents incompatible structural changes (BankData vs CardData) for existing accounts.
- `BankData` is only merged and persisted for `type = BANK` accounts; `CardData` is only merged and persisted for non-BANK accounts.

### 3.5 Soft Delete

Source: `model/account/FinancialAccountEntity.kt` (`deleted_at` column), `V0_3__create_banking_accounts.sql`

- Accounts are **never hard-deleted** because they are referenced by transactions.
- A `deleted_at IS NULL` partial index (`idx_banking_financial_accounts_active`) is used for active account lookups.
- The domain repository interface (`FinancialAccountRepository`) does not expose a delete method. A `deleteFinancialAccount` mutation is **absent from the GraphQL schema** (as of this reading). Backlog work still exists both in `docs/03-features/personal-finance/backlogs/phase-1-accounts-cards.md` and in `docs/00-planning/backlog.md` (`BK-11`), but it is not yet implemented in the GraphQL API.

### 3.6 Card Last-Four-Digit Extraction

Source: `FinancialAccountService.extractLastFourDigits()`

- The `card_last_four_digits` column is derived from `cardData.maskedNumber` by stripping all non-digit characters and taking the last 4 digits.
- Extraction returns null if the resulting digit string has fewer than 4 digits.
- This derived field is used by `FinancialAccountRepository.findCardAccountsByLastFourDigits()` for card matching during import flows.
- DB index `idx_banking_financial_accounts_last4_active` covers `(account_id, card_last_four_digits)` where `deleted_at IS NULL` and `card_last_four_digits IS NOT NULL`.

### 3.7 Currency

- Defaults to `"BRL"` when not provided or blank.
- Stored as `CHAR(3)` (ISO 4217). The current `finance-transactions` drawer keeps currency hidden and defaults manual accounts to `BRL`; foreign-currency account UX remains future work.
- Currency is not changeable on update if the field is absent or blank (existing value is preserved).

### 3.8 Future-Use Flags & Visual Metadata

- Both `includeInNetWorth` and `includeInDashboard` default to `true` when not supplied at creation.
- `includeCashInAllocation` also defaults to `true` when not supplied at creation.
- On update, if omitted, existing values are preserved.
- `themeColor` is persisted when supplied, but the current `finance-transactions` drawer hides this input.
- These fields exist in the domain model and GraphQL schema but are intentionally **out of the current transaction-scope UX**. They should not drive product expectations for this screen until explicitly brought back into scope.

### 3.9 Display Mode in Transaction Scope

Source: `web/src/app/personal-finance/finance-transactions/account/useAccountDisplayMode.ts`

- The current `finance-transactions` page uses **calendar-based display for all supported account types**, including credit and charge cards.
- Bill-based display has been intentionally deferred pending product decisions about how to handle cards with missing or unreliable billing-cycle metadata.

### 3.10 Bill Cycle (Credit/Charge Cards)

Source: `service/transaction/CreditCardBillService.kt`, `V0_3__create_banking_accounts.sql`

- Bills are auto-created on the first transaction within a billing cycle, using `closingDay` and `dueDay` from `CardData`.
- Each card has at most one bill per `closing_date` (unique constraint `uq_credit_card_bills_account_closing`).
- `BALANCE_ADJUSTMENT` transactions are never assigned to a bill.
- `linkedBankAccountId` on `CardData` optionally links to a bank account; when set, bill payment auto-creates the debit leg on that bank account.
- The current `finance-transactions` create/edit drawer does **not** expose `linkedBankAccountId`.
- In the current UI, billing-cycle inputs are shown only for `CREDIT_CARD` and `CHARGE_CARD`. `PREPAID_CARD` and `VOUCHER_CARD` do not expose bill-cycle fields and continue to behave as calendar-scoped accounts.

### 3.11 Quota (Planned, Not Yet Enforced)

Source: comment in `FinancialAccountService.create()`

- A plan-based quota on account creation is planned but not implemented:
  - FREE plan: 5 accounts
  - BASIC plan: 20 accounts
  - PRO plan: 100 accounts
- Currently there is **no limit** enforced at creation.

## 4. User Scenarios

**Scenario 1 — Create a BANK account (happy path)**
User opens the account creation drawer, selects "Conta Bancária", chooses a subtype (e.g., `CONTA_CORRENTE`), selects an issuer from the searchable list (e.g., Itaú), optionally enters branch code, account number, and check digit, provides an initial balance and date, and submits. The system creates the account and auto-creates a `BALANCE_ADJUSTMENT` transaction for the initial balance.

**Scenario 2 — Create a BANK account with custom institution**
User selects "Conta Bancária" but the institution is not in the list. User picks "Custom" (sentinel value `"custom"` in the UI), enters a free-text institution name. The system stores `issuerName` and sets `issuerId = null`.

**Scenario 3 — Create a CREDIT_CARD account (happy path)**
User selects "Cartão", sets subtype to `CREDIT_CARD`, optionally picks network and level, optionally enters the last 4 digits and credit limit, and may provide closing day and due day when known. The system creates the account. Bills are auto-created when the first transaction is posted.

**Scenario 4 — Create a CHARGE_CARD account**
Same as Scenario 3 except subtype is `CHARGE_CARD`. Billing-cycle fields remain optional. `cardLevel` is not shown (UI only renders the card level selector for `CREDIT_CARD`).

**Scenario 5 — Create a VOUCHER_CARD or PREPAID_CARD**
User selects "Cartão", sets subtype to `VOUCHER_CARD` or `PREPAID_CARD`. These subtypes are not billing-cycle cards (`isBillingCycleCard = false`), so closing day, due day, and credit limit are not shown. The UI may still capture the last 4 digits, but the account remains calendar-scoped and does not depend on bill-view behavior.

**Scenario 6 — Edit an existing account**
User opens the edit drawer for an existing account. The type selection step is skipped (step jumps to 2). The `initialBalance` and `initialBalanceDate` fields are hidden. Subtype, name, issuer, and subtype-specific bank/card data can be modified. Account type cannot be changed across the BANK / non-BANK boundary. Hidden future-use fields such as `themeColor` and inclusion flags are not part of the current drawer UX.

**Scenario 7 — Initial balance date too old**
User enters an initial balance with a date older than 5 years. The backend throws `ValidationException` with error code `TRANSACTION_DATE_OUTSIDE_ALLOWED_WINDOW`. The frontend validates this client-side using `getFinanceMinAllowedDate()` before submission.

**Scenario 8 — Initial balance is zero**
User enters `0` as the initial balance. The backend throws `IllegalArgumentException` (`initialBalance must be non-zero when provided`). The frontend validates this client-side before submission.

**Scenario 9 — Create account without issuer**
User submits without selecting an issuer and without entering a custom institution name. The backend throws `IllegalArgumentException`. The frontend validates this client-side and blocks submission.

**Scenario 10 — Card account created inline from bill import**
The `CreateFinancialAccountDrawer` accepts `initialMaskedNumber`, `initialClosingDay`, `initialDueDay`, `initialIssuerId`, and `initialIssuerName` props. These pre-fill the form fields when the drawer is opened from the bill import flow. After successful creation, the `onCreated` callback receives `closingDay` and `dueDay` for the caller to use.

**Scenario 11 — List accounts**
The `financialAccounts` query returns all non-deleted accounts for the authenticated tenant. Issuer data is batch-loaded (one extra query for all distinct `issuerIds`) to avoid N+1 queries.

**Scenario 12 — Account with linked bank account for bill payment**
A credit card account may have `cardData.linkedBankAccountId` set to a bank account's ID. When the user pays a bill (`payBill` mutation), the system auto-creates a debit transfer on the linked bank account. This is a backend capability; the current `finance-transactions` create/edit drawer does not expose this field.

## 5. Validations & Restrictions

### Field-level validation

| Field | Rule | Enforced in |
|---|---|---|
| `type` | Required; must be one of the 8 enum values | DB CHECK, GraphQL enum |
| `subtype` | Required; must be one of the 22 enum values | DB CHECK, GraphQL enum |
| `issuerId` or `issuerName` | At least one must be present; mutually exclusive | Service layer (`require`) |
| `name` | Derived from issuer if omitted; must resolve to a non-blank string | Service layer |
| `currencyCode` | ISO 4217, 3 chars; defaults to `BRL` | DB CHAR(3) |
| `initialBalance` | Must be non-zero if provided | Service layer (`require`) |
| `initialBalanceDate` | Required when `initialBalance` is provided | Service layer (`require`) |
| `initialBalanceDate` | Must not be older than 5 years from today | Service layer (`ValidationException`) + frontend |
| `cardData.closingDay` | Optional integer; when present must be between `1` and `31`; no pairing/order rule with `dueDay` | DB CHECK + service layer + frontend |
| `cardData.dueDay` | Optional integer; when present must be between `1` and `31`; no pairing/order rule with `closingDay` | DB CHECK + service layer + frontend |
| `cardData.cardNetwork` | Must be one of 8 enum values if provided | DB CHECK |
| `cardData.cardLevel` | Must be one of 5 enum values if provided | DB CHECK |
| `connectionStatus` | Must be one of 6 enum values if provided | DB CHECK |
| Type change (update) | BANK ↔ non-BANK change is rejected | Service layer (`require`) |

### Ownership & tenancy

- All queries and mutations are scoped by `accountId` (tenant), resolved from the JWT principal. Users cannot access or modify accounts belonging to other tenants.
- `createdByUserId` is an audit-only field and is never changed on update.

### Soft-delete transparency

- All repository queries filter `deleted_at IS NULL`. Deleted accounts are invisible to the application but remain in the database.

## 6. Open Questions / Gaps

**6.1 Soft-delete / deactivate account is still backlog work.**
The data model already supports soft deletion via `deleted_at`, but there is still no `deleteFinancialAccount` / deactivate mutation in the GraphQL schema and no UI flow in `finance-transactions`. Treat deletion/deactivation as future work, not as a supported user capability today. The current planning backlog tracks this under `BK-11`.

**6.2 Future-use fields remain in the API/domain but are intentionally hidden in the current UI.**
`themeColor`, `includeInNetWorth`, `includeInDashboard`, `includeCashInAllocation`, `currencyCode`, and `linkedBankAccountId` still exist in the model and GraphQL contract. However, the current `finance-transactions` account drawer intentionally hides them. Product/spec discussions should not assume those controls are available to end users in this scope.

**6.3 Bill view is deferred in the transaction UI.**
Backend bill lifecycle support still exists, but the `finance-transactions` page intentionally stays in calendar mode for all accounts until the product decides how bill-scoped navigation should behave for cards that do not expose reliable billing-cycle data or do not have a bill concept at all.

**6.4 BIN enrichment is not implemented in the backend.**
The backlog describes BIN lookup to auto-fill `cardNetwork`, `issuerName`, and `cardLevel`. No BIN enrichment service or lookup is present in the backend code. The `bin` field is stored as provided but never acted upon server-side.

**6.5 The current transaction-scope UI exposes only BANK and CARD entry points.**
The frontend type selection only presents two top-level choices: "Conta Bancária" (maps to `BANK`) and "Cartão" (maps to `CREDIT` / `PAYMENT` card subtypes). Account types `CASH`, `INVESTMENT`, `LOAN`, `ASSET`, and `BENEFIT` still exist in the data model and GraphQL schema, but there is no creation path for them in the current `finance-transactions` drawer.

**6.6 Account name uniqueness is documented but not enforced.**
The backlog (`phase-1-accounts-cards.md`, Error Handling section) states "Validate account name uniqueness per user." No unique constraint exists in `V0_3__create_banking_accounts.sql` on `(account_id, name)`, and the service layer performs no uniqueness check.

**6.7 `logoKey` is stored in `financial_accounts` but never written by the service.**
The `FinancialAccount` domain model has `logoKey: String?` and the DB column `logo_key` exists, but `FinancialAccountService.create()` does not populate it. It is not part of `CreateFinancialAccountCommand` or `UpdateFinancialAccountCommand`. The issuer's logo is accessed through the `Issuer` entity join at query time.

**6.8 Account quota enforcement is absent.**
The code contains a `TODO` comment indicating plan-based account creation limits (FREE: 5, BASIC: 20, PRO: 100) are planned but not yet enforced. There is no guard at creation time.

**6.9 `linkedBankAccountId` exists only as backend/API capability today.**
The field has a concrete meaning: it points to the bank account that should receive the debit leg of a bill payment. However, the current manual-account UI does not let the user define or edit this link yet.
